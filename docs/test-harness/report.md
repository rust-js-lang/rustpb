# Recorded oracles make RustPB's claims checkable

The most trustworthy harness RustPB can build puts three implementations behind one wire protocol. ScalaPB runs as a warm JVM worker, rustpb runs natively, and rustpb runs again as rust-js output under Bun and Node. All three speak the framing that Google's conformance runner already uses: a 4-byte little-endian length, then a serialized `ConformanceRequest` or `ConformanceResponse`. ScalaPB's answers are **recorded and committed as fixtures**, so every pull request compares rustpb, native and JS, against ScalaPB without starting a JVM. A nightly job asks the live oracle again to catch drift in the oracle itself. Google's runner then plays a narrower role than the design gives it. It **measures** ScalaPB plus scalapb-jsoniter 0.1.2 and produces the exact failure list rustpb must reproduce. It also shows where ScalaPB and rustpb share a deviation from the spec, which a differential test cannot see. Coverage-guided fuzzing runs only on the native Rust side. Its corpus is then replayed through ScalaPB and JS in batches, because a JVM cannot sit inside a fuzz loop. Single-sided properties, a model of the default-construction graph, random and adversarial schemas, and a small set of Kani proofs cover what no oracle can judge. This matters because RustPB's promise is unusual. It is not "conforms to protobuf" but "equals one pinned ScalaPB deployment, byte for byte and JSON digit for digit, on native and JS". Users will trust that promise only if every claim links to evidence a machine produced. The design's §6 already has most of the right oracles. It gets four things wrong: live differential fuzzing on every change, a failure list that cannot fail on skips, Kani "proving" emitted JavaScript, and leaving rust-js until milestone 5. It also lacks the protocol, fixture conventions, generator testing and evidence pipeline that bind the oracles together.

## Every oracle has a blind spot the others cover

No single oracle can carry RustPB's contract, and the most trusted libraries say so in their structure. SQLite runs four independent harnesses. One of them, SQL Logic Test, runs **7.2 million queries differentially against four other database engines**. SQLite also measures the suite itself, calling coverage "a test of the test suite", and keeps **590 times as much test code as library code** ([How SQLite Is Tested](https://www.sqlite.org/testing.html)). RustPB's version of that structure has five oracles. Each one decides a different question, and each fails in a predictable way.

**The ScalaPB worker is the authority, and it must be long-lived.** RustPB's contract is equality with a ScalaPB 0.11.x deployment that uses scalapb-jsoniter 0.1.2. Only ScalaPB can decide the cases that matter most: a known field with the wrong wire type, unknown-field grouping, `-0.0` omission, the 0.1.2 JSON leniencies and mapper failures. ScalaPB already ships a conformance testee, `ConformanceScala.scala`. It is about 160 lines with the standard framing, and it is identical on master and the 0.11.x branch. But it uses **scalapb-json4s rather than scalapb-jsoniter**, and it is built against a **protobuf 3.19.6** runner ([ConformanceScala.scala](https://github.com/scalapb/ScalaPB/blob/master/conformance/src/main/scala/ConformanceScala.scala), [build_test_runner.sh](https://github.com/scalapb/ScalaPB/blob/master/conformance/build_test_runner.sh)), so its failure list says nothing about RustPB's JSON contract. scalapb-jsoniter has no conformance runner at all. Its tests compare against Java's `JsonFormat` ([scalapb-jsoniter tests](https://github.com/scalapb/scalapb-jsoniter/tree/master/core/shared/src/test/scala/scalapb_jsoniter)). The oracle therefore has to be built. Take ScalaPB's testee, replace json4s with jsoniter 0.1.2's `Parser` and `Printer` configured exactly as the app's codec, and look up companions by any message full name in `message_type`, not just `TestAllTypesProto3`. Hosting matters more than anything else about it. A December 2025 cross-language differential fuzzer measured **about 3 seconds per input to spawn a Java subprocess, against about 21.5 ms for a native binary**. It moved Java in-process through JNI to reach single-digit milliseconds after warm-up, and fell back to a long-running process exchanging inputs through shared memory at **6–15 ms per call** ([Differential Fuzzing Across The Language Divide](https://r9295.github.io/posts/differential-fuzzing-accross-languages)). A warm worker on stdin and stdout keeps JVM crashes, hangs and garbage-collector threads out of the fuzzer's process, and it reuses a protocol ScalaPB already speaks.

**Google's conformance runner is a measuring instrument, not the contract.** The runner holds every test case in one C++ program and drives a testee over pipes. A proto3 binary-plus-JSON run has **1,476 tests** at runner v33.0.0 (1,143 required and 333 recommended) ([Buf baseline_proto3](https://github.com/bufbuild/protobuf-conformance/tree/main/impl/baseline_proto3)). Its failure list is strict in both directions: a listed test that passes fails the run, and a listed failure whose message changes is reported ([conformance_test.cc](https://github.com/protocolbuffers/protobuf/blob/main/conformance/conformance_test.cc)). It has two properties the design does not account for. First, **skips never fail a run**: `ReportSkip` only records the test. rustpb is proto3-only and will answer `skipped` to every proto2 and text-format request, so a testee that skipped *everything* would print "CONFORMANCE SUITE PASSED". Second, most tests judge the output by parsing it with the C++ implementation and comparing with `MessageDifferencer` with NaN treated as equal. **Byte order, JSON key order and number spelling are therefore not compared**, except in tests that set `require_same_wire_format` ([conformance_test.cc `VerifyResponse`](https://github.com/protocolbuffers/protobuf/blob/main/conformance/conformance_test.cc)). The runner cannot show that rustpb's float digits equal jsoniter's; only the ScalaPB worker can. What the runner *can* do is expose shared deviations. Differential testing "cannot see non-compliances shared by all implementations" ([VUPER](https://arxiv.org/pdf/2608.09094)). If ScalaPB and rustpb both fail `UnknownOrdering` the same way, the differential test passes silently, while the runner's list names the deviation. That deviation is real. The test requires that unknown values under one field number keep their interleaved wire types, and protobuf-java lists it as a known failure ([failure_list_java.txt](https://github.com/protocolbuffers/protobuf/blob/main/conformance/failure_list_java.txt)). ScalaPB's `UnknownFieldSet` groups values by wire type in a hash map ([UnknownFieldSet.scala](https://github.com/scalapb/ScalaPB/blob/master/scalapb-runtime/src/main/scala/scalapb/UnknownFieldSet.scala)), and the design deliberately copies that.

**Native against JS is a second differential, and it needs its own guards.** rust-js's own record shows how much this axis finds. Of **357 P0 wrong-answer bugs** in ten days, **76 came from generated tables** and **57 from metamorphic rewrites**, all checked against native Rust ([finding-wrong-answers.md](https://github.com/rust-js-lang/rust-js/blob/HEAD/docs/finding-wrong-answers.md)). Its numbers grid alone runs **83,017 cases** of boundary values against native. Two of its lessons apply directly to RustPB. "A program all refused passes all": if rust-js refuses a generated module, every JS case in that batch is vacuous. And "every accepted difference is a claim to re-test". protobuf-es shows what a JS conformance testee looks like. With BigInt its failure list is empty. Without BigInt it fails exactly the unquoted int64 and uint64 JSON number tests ([failing_tests_without_bigint.txt](https://github.com/bufbuild/protobuf-es/blob/main/packages/protobuf-conformance/failing_tests_without_bigint.txt)), which marks where a JS build is weakest. The JS axis also has engine-specific edges the native build never meets. The maximum string length is **2^29−24 UTF-16 units on V8 against 2^31−1 on JavaScriptCore** ([rust-js ADR 0682](https://github.com/rust-js-lang/rust-js/blob/HEAD/docs/decisions/0682-a-js-strings-length-is-at-most-int32-max.md)). A stack overflow is a `RangeError` on V8 and JavaScriptCore but an `InternalError` on SpiderMonkey ([rust-js ADR 0692](https://github.com/rust-js-lang/rust-js/blob/HEAD/docs/decisions/0692-a-thrown-error-is-a-panic-and-what-js-threw.md)). A depth bomb must fail cleanly on the smallest stack among them.

**Single-sided properties judge what no second implementation can.** prost's fuzz oracle checks three things: `encoded_len` equals the bytes written, re-encoding the decoded value is stable, and the two encode paths agree. Its own doc warns that this works only with `BTreeMap` fields, because `HashMap` entry order breaks byte comparison ([prost tests/src/lib.rs](https://github.com/tokio-rs/prost/blob/v0.14.6/tests/src/lib.rs)). buffa compares through a `serde_json::Value` with sorted keys for the same reason, and to sidestep `NaN != NaN` ([buffa fuzz/src/lib.rs](https://github.com/anthropics/buffa/blob/HEAD/fuzz/src/lib.rs)). These properties are cheap, need no JVM and run inside the fuzz loop. Three more belong beside them. Decoding the concatenation `a ++ b` must equal merging the two decoded values, which is protobuf's own merge rule. For mapped fields the property must hold on base values *before* mapping, because §4.1 merges base values and maps once. Unknown fields must be preserved: decode with a schema that lacks fields, re-encode, decode with the full schema and get the same value. And a never-panic property holds for every input.

**Kani proves arithmetic exhaustively, and nothing else.** Kani needs an unwind bound one more than the loop count, and a proof holds only up to the buffer size it was given ([Kani loop unwinding](https://model-checking.github.io/kani/tutorial-loop-unwinding.html)). That suits RustPB's small fixed-size functions. A varint is at most ten bytes, so Kani can prove `decode_varint(encode_varint(x)) == x` for every `u64`, check `encoded_len_varint` against the actual length, prove zigzag round trips, and show that decoding any buffer of eleven bytes or fewer never panics. It can also prove the length-prefix check never reads past its parent for any declared and remaining pair. These proofs cover all inputs, which proptest cannot. Whole-message encode and decode, with unbounded `Vec`s and `HashMap`s, is a poor Kani target and belongs to properties and fuzzing. The design has already corrected one point: prost Kani-checks only `Timestamp` and `Duration` in prost-types, never its varint code ([prost KANI.md](https://github.com/tokio-rs/prost/blob/HEAD/KANI.md)). RustPB writes its own proofs over `rustpb::wire`, and those prove what RustPB actually calls.

| Oracle | Decides | Blind to | Cost per input |
|---|---|---|---|
| ScalaPB worker (ScalaPB 0.11.x, jsoniter 0.1.2) | Exact bytes, JSON text, accept or reject, error class | Deviations ScalaPB shares with rustpb | ms when warm; seconds per spawn |
| Google runner | Spec behaviour on `TestAllTypesProto3`; shared deviations | JSON spelling and byte order (mostly); skipped tests | One run per suite |
| Native vs JS | rust-js lowering, BigInt, `Uint8Array`, engine limits | Bugs in both builds' shared Rust source | µs native, ms JS |
| Single-sided properties | Size vs write, stability, merge rule, no panic | Any behaviour that is consistently wrong | µs |
| Kani | All-inputs truth of varint, zigzag, length checks | Everything above a single function | Minutes per job |

## The obvious design breaks in five specific places

The design's §6 names the right oracles. Wired the obvious way, five of them would give false confidence, and each failure has a precedent.

**A JVM cannot sit inside a coverage-guided loop.** §6.7 says mutated bytes and JSON are "fed to both decoders" and that "CI fuzzes every change (CIFuzz-style, time-boxed)". At seconds per JVM spawn, or milliseconds per call over a pipe, against microseconds for a native decode, a ScalaPB call on each execution would make the fuzzer thousands of times slower. The working cross-language fuzzers take coverage from **one implementation only** ([r9295](https://r9295.github.io/posts/differential-fuzzing-accross-languages)). The EVM fuzzer used Go through a LibAFL shim; beacon-fuzz embedded the JVM through JNI only because its clients were the system under test ([beacon-fuzz](https://github.com/sigp/beacon-fuzz)). RustPB should fuzz natively, with the single-sided oracles running in the loop. It should then **replay the growing corpus** through the ScalaPB worker and the JS testee in batches, and commit the recorded outcomes. The per-PR comparison becomes deterministic and replayable, and fuzzing time only buys new inputs. "As prost does" does not carry over either. prost's CIFuzz depends on its OSS-Fuzz membership ([prost cifuzz.yml](https://github.com/tokio-rs/prost/blob/v0.14.6/.github/workflows/cifuzz.yml)), and OSS-Fuzz requires "a significant user base and/or be critical to the global IT infrastructure" ([OSS-Fuzz acceptance](https://google.github.io/oss-fuzz/getting-started/accepting-new-projects/)). A new project will not qualify. ClusterFuzzLite provides the same modes on GitHub Actions: `code-change` per PR with a **600-second default**, `batch`, a mandatory daily `prune`, and `coverage` ([ClusterFuzzLite](https://google.github.io/clusterfuzzlite/running-clusterfuzzlite)).

**An exact failure list still passes a testee that skips everything.** §6.8 states the list rule correctly but misses the skip hole. The harness must assert the *answered* set. It should count requests on the testee side, or parse `--verbose`, and require exactly the proto3 binary-plus-JSON tests of the pinned runner version to be answered. A runner upgrade then appears as a reviewed change to a committed count. `--record_requests` writes one line per request with a CRC, so diffing it pins the corpus across upgrades ([conformance_test_runner.cc](https://github.com/protocolbuffers/protobuf/blob/main/conformance/conformance_test_runner.cc)). The design also expects the JSON list to be *written*, as "every deliberate scalapb-jsoniter 0.1.2 deviation". It should be *measured* instead. Run the same runner against the ScalaPB worker, which compiles `TestAllTypesProto3` with ScalaPB 0.11.x and parses with jsoniter 0.1.2, and commit the list it produces. rustpb's native list, its JS list and the ScalaPB list must then be **identical**, and that equality is a test of its own. Quoted booleans, leading zeros, trailing commas and comments are tests 0.1.2 might accept. Nobody knows today which ones it does; the measurement settles them. One more limit applies. `TestAllTypesProto3` imports `google.protobuf.Any` and the wrapper types ([test_messages_proto3.proto](https://github.com/protocolbuffers/protobuf/blob/main/src/google/protobuf/test_messages_proto3.proto)), and the design covers neither. Until rustpb supports them, the testee answers those requests through listed failures, not skips. They then stay visible and fail once fixed.

**Kani proves Rust, not the JavaScript rust-js emits.** §6.10 and §7 say Kani proves the two-32-bit-halves path "equal to the `u64` path". That holds while the halves path is Rust code. But §7's target is compiler-owned lowering, where rust-js *emits* the halves logic as JavaScript, and Kani never sees that. The honest split has two parts. Kani proves a Rust reference implementation of the halves algorithm equal to `u64`. A **numbers-grid table** then runs the emitted JS against native at every varint length from 1 to 10, crossed with boundary values near 2^31, 2^32, 2^53, 2^63 and 2^64−1. This is the technique that found rust-js's `f32` `div_euclid` bug on its first run ([finding-wrong-answers.md](https://github.com/rust-js-lang/rust-js/blob/HEAD/docs/finding-wrong-answers.md)).

**cargo-mutants cannot mutate generated code.** §6.5 says to "break the derive (swap a tag, drop zigzag, skip an unknown field)". cargo-mutants mutates source files and reports each mutant as caught, missed, unviable or timed out ([cargo-mutants book](https://mutants.rs/print.html)). Generated `.rs` files in `OUT_DIR` are build artifacts it never visits. The harness therefore needs two mutation layers. cargo-mutants covers the runtime, derive and build crates, `--in-diff` per PR and sharded in full nightly. A hand-written list of codegen mutations is applied to the generator's templates and run against the fixture suite, the way rust-js keeps its own mutation script. The harness should be mutated too. A JS testee patched to answer `skipped`, or a canonicalizer patched to sort *every* field, must turn CI red.

**Comparison must be canonical, and the judge must not be the defendant.** §6.2 says to compare by value where bytes are not deterministic: sets, maps and unknown-field order. Who decodes for that comparison matters. buffa parses the conformance envelope **by hand**, because "we must not use buffa (or a generated codec) to parse the test harness messages themselves" ([buffa conformance/src/main.rs](https://github.com/anthropics/buffa/blob/main/conformance/src/main.rs)). The same rule applies to RustPB's comparison: rustpb's own decoder must never decide whether rustpb's bytes are right. The comparison unit should be a canonical outcome record. It is either `ok` with re-encoded bytes, JSON text and a value dump that prints 64-bit numbers as decimal, or `err` with an error class. Error *classes* are compared, not messages, because a JVM exception text is not part of the contract. Resource-limit errors form their own class, as in wasmtime's `is_non_deterministic_error` ([wasmtime oracles/engine.rs](https://github.com/bytecodealliance/wasmtime/blob/HEAD/crates/fuzzing/src/oracles/engine.rs)). JSON comparison must keep numbers as raw text: parsing them would hide exactly the digit differences the contract forbids. The JS side adds its own trap. `JSON.stringify` throws on a BigInt, and `===` between a BigInt and a Number is always false, so the JS testee must print BigInts as decimal strings itself.

## Code generation is the risk no fixed corpus reaches

RustPB's novel surface is its code generator, not its codec. It has to handle 7,785 mapped fields, sealed oneofs in two styles, the defaultability fixed point and name collisions. A fixed `TestAllTypesProto3` exercises none of it. ScalaPB faced the same problem and solved it with random schemas. Its `GeneratedCodeSpec`, "Java and Scala protos are equivalent", generates random `.proto` files with nested messages, enums, oneofs and cross-file references. It compiles each schema with both protoc-java and ScalaPB, generates values for it, and checks bytes, parsing and conversions between the two ([GeneratedCodeSpec.scala](https://github.com/scalapb/ScalaPB/blob/master/proptest/src/test/scala/GeneratedCodeSpec.scala)). The test is tagged `Slow` and runs only 20 schemas, but it runs every time. No Rust protobuf generator does anything comparable. upb comes closest, building random MiniTable schemas from fuzz bytes with "links" taken modulo the count so any value is valid ([upb fuzz_util.h](https://github.com/protocolbuffers/protobuf/blob/main/upb/test/fuzz_util.h)). Compiler testing shows why a fixed corpus is not enough: Csmith reported **more than 325 bugs** and YARPGen **more than 220**, including bugs Csmith could not find, and compilers grow resistant to any one generator over time ([YARPGen OOPSLA'20](https://users.cs.utah.edu/~regehr/yarpgen-oopsla20.pdf)).

RustPB needs two schema generators. The **valid generator** ports ScalaPB's approach and adds the options ScalaPB never generates: `(rustpb.field).type` with test mappers, `no_box`, `required`, sealed oneofs of both styles, `collection_type = Set`, and `key_type` and `value_type`. Each schema is compiled by both ScalaPB and rustpb, and random values go through all three implementations. Compiling dominates the cost, so this runs as a nightly campaign, batching many schemas into one generated crate. The **adversarial generator** is the opposite. It seeks keywords, names that collide after snake or camel casing, `Option`, `Error`, `Empty` and `Unrecognized` names, deep nesting and default-edge cycles. Its property needs no compile: the generator never panics, under `catch_unwind`, and returns either code or a diagnostic. It must also be deterministic. The same input twice gives byte-identical output, and the output does not depend on file order or `HashMap` seed. rust-js's determinism net found a `HashSet` walk order that made `n + 1` wrap in **5 compiles out of 8** ([finding-wrong-answers.md](https://github.com/rust-js-lang/rust-js/blob/HEAD/docs/finding-wrong-answers.md)), and codegen ordered by a hash map is the documented failure mode. Because rustpb-build decodes descriptors with its own runtime (design §3 dec. 6), a raw-bytes libFuzzer target over the descriptor decoder plus the generator costs almost nothing.

The defaultability analysis is a pure function over a small graph, which suits model-based testing. The model is the specification written as simply as possible: a recursive `defaultable(m)` with explicit on-stack cycle detection. Random graphs with edge kinds {`no_box`, `required`, mapped base, optional, oneof, repeated} and `default = false` flags must give the same answer from the generator's fixed point and from the model. Monotonicity is checkable too. Adding `default = false` never makes a message defaultable, and turning a singular edge optional never makes one non-defaultable. The diagnostic's named cycle must be a real cycle in the input. All graphs up to three or four messages can be enumerated exhaustively in seconds. That catches corner cases a random sampler skips, and the design's seven hand fixtures in §4.1 become a special case.

The fixed-schema generator tests follow what the Rust protobuf crates already do. buffa builds `FileDescriptorProto`s in Rust and asserts on its error enum. It also runs an `#[ignore]`d compile matrix of `cargo check` over every feature subset of 25 fixture protos, which CI runs explicitly while sharing the workspace `target/` ([buffa feature_gating_compile.rs](https://github.com/anthropics/buffa/blob/HEAD/buffa-codegen/tests/feature_gating_compile.rs)). Golden output fits insta, whose `glob!` gives one snapshot per fixture and which never auto-accepts under `CI` ([insta](https://insta.rs/docs/advanced/)). "A non-defaultable message has no `impl Default`" is best enforced by a generated `static_assertions::assert_not_impl_any!` ([static_assertions](https://docs.rs/static_assertions/latest/static_assertions/macro.assert_not_impl_any.html)), which avoids trybuild's drift in `.stderr` snapshots across rustc versions. Generators for generated types should come from rustpb-build behind an `arbitrary` feature, as buffa emits them. buffa routes substituted types through their base type, "so the substituted type needs no `Arbitrary` impl" ([buffa codegen](https://github.com/anthropics/buffa/blob/HEAD/buffa-codegen/src/lib.rs)). proptest-derive cannot derive recursive types ([proptest-derive](https://docs.rs/proptest-derive/latest/src/proptest_derive/lib.rs.html)), and proto schemas routinely have them. For RustPB a mapped field becomes "arbitrary base value, then `to_custom`, discard on error". A mapper that rejects most base values should supply its own base strategy. This generator is the twin of §6.9's per-mapper `to_base(to_custom(b)) == b` property.

## The harness architecture

### One protocol, three testees, recorded outcomes

```
 inputs                         driver (Bun/TypeScript, harness/)
 ───────────────────            ─────────────────────────────────────────────
 fixtures/**/*.bin|json  ──┐    frames each case as  [len:u32 LE][ConformanceRequest]
 corpus/  (min. fuzz finds)├──► message_type = any full name; payload = bytes|json;
 Google runner's tests   ──┘    requested_output_format = PROTOBUF|JSON
                                   │                 │                  │
                                   ▼                 ▼                  ▼
                            ScalaPB worker     rustpb testee      rustpb testee
                            (JVM, warm;        (native, cargo)    (rust-js → Bun, Node)
                             record jobs +          │                  │
                             nightly only)          │                  │
                                   │        ConformanceResponse: bytes | json | error
                                   ▼                 ▼                  ▼
                            canonicalize (independent decoder; maps, sets, unknown
                            fields sorted; JSON numbers kept as raw text)
                                   │
                   ┌───────────────┴────────────────┐
                   ▼                                ▼
          record: write *.outcome          compare: native == JS == recorded
          (+ oracle provenance)            outcome; count answered cases
```

The testee is one Rust crate, built natively by cargo and as JavaScript by rust-js. It parses the envelope by hand, following buffa. Its loop is `read_exact` of 4 bytes, `u32::from_le_bytes`, `read_exact` of the body, handle, write, `flush`, and EOF on the length read ends it cleanly ([buffa main.rs](https://github.com/anthropics/buffa/blob/main/conformance/src/main.rs)). It dispatches on `message_type` to every generated message it was built with, and it returns raw output, never its own judgement. The same binary serves Google's runner, which passes trailing arguments through to the testee, and RustPB's own driver. A Rust panic kills the process. The runner records that as a `runtime_error`, which "will always indicate that the test failed" ([conformance.proto](https://github.com/protocolbuffers/protobuf/blob/main/conformance/conformance.proto)), and starts a fresh testee for the next test ([fork_pipe_runner.cc](https://github.com/protocolbuffers/protobuf/blob/main/conformance/fork_pipe_runner.cc)). So "never panics" is enforced on every malformed-input case for free, natively and in JS, as long as the JS testee never catches a thrown error and converts it into a `parse_error`. The driver is written in TypeScript under Bun, like rust-js's own harness. It decodes envelopes and canonicalizes outputs with an independent protobuf implementation, so rustpb never judges itself. The choice of that implementation is a recommendation; the notes did not evaluate one. The worker's 30-second default read timeout is too slow for the driver. The driver needs its own watchdog that kills and restarts a hung worker and records the input as a hang, since V8's lack of fuel is the cautionary example ([wasmtime differential.rs](https://github.com/bytecodealliance/wasmtime/blob/HEAD/fuzz/fuzz_targets/differential.rs)).

### Components and where each lives

The split between a **public worker** and a **private worker** is new. RustPB's evidence must stand on its own, so it cannot depend on a private application's 858 schemas. The design's golden generator lives "in the Scala app" (§6.1), which is right for the app's mappers and real data but invisible to anyone outside.

| Component | Lives in | What it holds | Runs in |
|---|---|---|---|
| `conformance/testee` | rustpb repo | Hand-parsed envelope; dispatch by `message_type`; raw outcome | Every tier, native and JS |
| `oracle/scalapb-worker` (public) | rustpb repo, sbt project | ScalaPB 0.11.x pinned exactly, scalapb-jsoniter 0.1.2, protobuf-java version recorded; compiles `TestAllTypesProto3` and rustpb's own test protos with ScalaPB options and test TypeMappers | Record jobs (path-filtered), nightly, release |
| App worker (private) | The Scala app's build, same worker source | The app's generated code and its ~223 TypeMappers; real stored records and queue messages | App's CI, nightly; results reported as counts only |
| Google runner | Pinned npm `protobuf-conformance` (36.2.0 today) or a commit-pinned CMake build | Test protos via `conformance_proto_eject`, so protos and runner always agree | Per-PR |
| Failure lists | `conformance/failure_list_{scalapb,native,js}.txt` | One line per test, `# reason, ADR or §` | Per-PR, with the three-way equality test |
| Fixtures | `fixtures/` | Inputs, recorded outcomes, provenance | Fast loop onward |
| Fuzzing | `fuzz/` (excluded from the workspace, as buffa does); `corpus/` committed and minimized | Decode, encode-from-`Arbitrary`, JSON per-format and descriptor targets | Per-PR 300–600 s; nightly batch |
| Properties | Each crate's `tests/`; generators from rustpb-build's `arbitrary` feature | Size, stability, merge, unknown preservation, mapper round trip | Fast loop (256 cases); nightly (high count) |
| Kani | `#[cfg(kani)]` inside `rustpb::wire` | Varint, zigzag, length check, halves reference | Per-PR, own job, pinned action |
| Generator tests | `rustpb-build/tests/` | Diagnostics as data, insta goldens, `#[ignore]` compile matrix, determinism, defaultability model | Fast loop and per-PR |
| Schema generators | `harness/schemagen/` | Valid and adversarial `.proto` generators | Per-PR (never-panic, determinism); nightly (compile and compare) |
| End to end | `e2e/` | Native server on port 0; rust-js Playwright runner | Per-PR (Chromium); nightly (all three engines) |
| Evidence | `harness/report/` | Generates `docs/TESTING.md` and the results matrix from CI artifacts | Release, plus nightly preview |
| rust-js hook | rust-js repo | rustpb's generated code and `#[test]`s in rust-js's nightly crate corpus | rust-js's nightly |

Two choices in the table reverse the obvious ones. **Recording beats live comparison per PR.** The per-PR tier never starts a JVM. Any PR that adds or changes a fixture triggers a path-filtered record job that asks the public worker and commits the outcome. The nightly job asks again for every fixture and fails on any difference, which catches drift in the oracle's own version. **Each test-message source is pinned to its runner.** buffa pins its runner build by commit because "a tag can move without a review of this file" ([buffa Dockerfile.tools](https://github.com/anthropics/buffa/blob/main/conformance/Dockerfile.tools)). Ejecting the test protos from the runner package keeps rustpb from meeting `edition = "2026"` syntax by accident; several unittest files on protobuf main have already moved to it.

### Fixture conventions

JSONTestSuite's convention transfers almost unchanged. Its file name carries the expected result: `y_` must accept, `n_` must reject, `i_` is implementation-defined ([JSONTestSuite](https://github.com/nst/JSONTestSuite)). For RustPB every expectation is ScalaPB's recorded behaviour, so the prefixes mean something slightly different. `y_` means ScalaPB accepts and the recorded value is the expectation. `n_` means ScalaPB rejects and the recorded error class is the expectation. `i_` means the spec allows either answer, RustPB matches ScalaPB, and other implementations may differ. That last set includes wrong wire type as unknown, `-0.0` omission and the 0.1.2 JSON leniencies, which are the rows a results matrix should highlight. Each file name carries a stable rule ID from the design, such as `fixtures/binary/4.6-depth/n_4.6-depth_unknown-group_101.bin`, so a script can list design rules with no fixture. Each input sits beside a `.outcome` file holding the canonical outcome record. One `PROVENANCE` file per directory records the exact ScalaPB, scalapb-jsoniter and protobuf-java versions, the worker commit and the recording date. Bumping the pinned ScalaPB version is then a reviewed change that re-records every outcome and shows the diff.

Every bug becomes permanent in one commit, three ways. SQLite's rule is that a bug "is not considered fixed until new test cases that would exhibit the bug have been added" ([How SQLite Is Tested](https://www.sqlite.org/testing.html)). upb pins fuzzer findings as named tests with literal inputs, and protobuf-go replays its committed corpus as an ordinary `go test` ([protobuf-go fuzztest.go](https://github.com/protocolbuffers/protobuf-go/blob/HEAD/internal/fuzztest/fuzztest.go)). For RustPB the three artifacts are a minimized fixture with its recorded outcome, a copy in each fuzz target's seed corpus, and a named `regression_<issue>` test replayed by all three testees. Minimizing must preserve *the same disagreement*, not just "a failure". The reducer's interestingness test compares the outcome pair, as C-Reduce-style reducers do ([Regehr](https://blog.regehr.org/archives/1069)). Otherwise a reduced input can flip into an unrelated disagreement. proptest persists the failing *seed*, not the value, so a changed strategy can stop reproducing it ([proptest failure persistence](https://proptest-rs.github.io/proptest/proptest/failure-persistence.html)). Shrunk inputs must therefore also be copied into named fixtures. CI fixes `PROPTEST_RNG_SEED` from the commit hash and prints it.

Some fixture rows must be added to §6.4's table. Varint boundaries 0, 127, 128, 16383, 16384, 2^31−1, −1 as int32 (ten bytes), 2^63−1 and 2^64−1. A ten-byte varint whose last byte carries overflow bits: buffa rejects it while C++ and prost discard the bits, and protobuf-java's rule is unverified, so ScalaPB's recorded answer decides it. A packed `fixed32` whose length is not a multiple of four. Map entries with the value before the key, duplicate keys, and unknown fields inside the entry. A packed repeated enum holding `Unrecognized(-1)`. Every depth limit tested at limit−1, limit and limit+1 for each recursive shape: message, map value, unknown group and JSON nesting. SQLite tests "right to the edge of its defined limits" and just beyond ([How SQLite Is Tested](https://www.sqlite.org/testing.html)), and RUSTSEC-2024-0437 was exactly a recursion path that bypassed an existing limit ([RustSec](https://rustsec.org/advisories/RUSTSEC-2024-0437)). The design's 100-level depth is assumed to match ScalaPB, but nobody has checked it, and the limit−1/limit/limit+1 fixtures against the worker settle it.

### Test tiers and time budgets

Each tier is a strict superset of the one below it, following SQLite's split between "veryquick" (a few minutes, before each check-in) and the full and soak runs before release ([How SQLite Is Tested](https://www.sqlite.org/testing.html)). The budgets below are targets, anchored on prost's **300-second** per-PR fuzz, ClusterFuzzLite's 600-second default, and rust-js's full suite of **11–13 minutes on two machines** ([rust-js TESTS.md](https://github.com/rust-js-lang/rust-js/blob/HEAD/TESTS.md)). Every step runs under a hard timeout of about twice its usual time, so a hang ends instead of being waited on.

| Tier | Budget (wall clock) | Contents | Needs JVM? |
|---|---|---|---|
| Fast loop (`cargo test`, local) | ≤ 60 s | Unit tests; every `y_/n_/i_` fixture against its committed outcome; replay corpus (a few thousand cases, SQLite's `fuzzcheck` idea); properties at 256 cases; insta goldens; generator diagnostics; defaultability model on exhaustive small graphs | No |
| Per PR | ≤ 15 min, sharded with nextest `hash:` partitions | Fast loop; fixtures and corpus through the JS testee on Node and Bun; Google runner native and JS (binary and JSON) with strict lists, answered-count assertion and three-way list equality; compile matrix; generate-twice determinism; adversarial-schema never-panic run; Kani job; ClusterFuzzLite `code-change` 300–600 s on single-sided targets; `cargo mutants --in-diff` (non-blocking at first); e2e on Chromium; semver checks, MSRV, 32-bit check, `minimal-versions`; bundle-size diff; protox vs protoc on the test protos; record job only when fixtures change | Only the path-filtered record job |
| Nightly | ≤ 6 h, parallel | Live re-record and diff of every outcome; ScalaPB and JS replay of new corpus entries; ClusterFuzzLite `batch`, `prune`, `coverage`; every-prefix and every-bit-flip sweeps native and JS; peak-allocation checks; valid-schema campaigns through all three implementations; high `PROPTEST_CASES`; full sharded cargo-mutants plus the codegen mutation list; Miri on a codec subset; nightly branch coverage; Playwright on Chromium, Firefox and WebKit; full varint numbers grid; schema-evolution matrix; private app worker over the 858 protos and a real-data sample; performance trend | Yes |
| Release | ≤ 1 day | Nightly plus a soak (long fuzz, maximum property cases); re-verified pins of the runner version, test count and oracle versions; semver checks on a generated-API fixture crate; regenerated `TESTING.md`, results matrix and failure-list counts; release provenance | Yes |

Some placements need explaining. Kani goes per PR because its harnesses are few and cheap, and prost runs it as one CI job, though no timing was found. Prost recommends pinning the Kani action "because of instability in Kani internals" ([prost KANI.md](https://github.com/tokio-rs/prost/blob/HEAD/KANI.md)). Miri is nightly, not per PR, because the runtime has no `unsafe` (§3 dec. 5). Its value lies in dependencies: prost's string merge uses `unsafe`, and so does `bytes`. Miri is also slow and "fundamentally cannot ensure that your code is sound" ([Miri README](https://github.com/rust-lang/miri)). The anomaly sweeps are cheap natively. As an illustration, not a measurement, 10,000 golden messages of 200 bytes give 2 million prefixes and 16 million bit flips. The expectations come from invariants: `Err` or `Ok`, never a panic, an `Ok` re-encodes stably, and peak allocation stays within a small multiple of the input length under a counting allocator. That last check is the codec version of SQLite's out-of-memory loop, since Rust's `Vec` aborts rather than failing. Playwright runs with `retries: 0` and one worker in CI, which its documentation recommends "to prioritize stability and reproducibility" ([Playwright CI](https://playwright.dev/docs/ci)). A flake then gets investigated rather than hidden. The e2e server binds port 0 and prints its port, keeps connect-rust's "is the process still alive?" readiness loop, and echoes the raw body in hex alongside its decoded value. The browser test then asserts byte equality of what crossed the wire, not just that a reply arrived.

### Evidence published to users

Trust comes from evidence a reader can check, generated so it cannot drift. SQLite's single page lists harness sizes, test counts, the coverage method, the anomaly methods and the fuzzing history, with a last-updated stamp ([How SQLite Is Tested](https://www.sqlite.org/testing.html)). Buf publishes per-implementation failure counts as badges, split into Required and Recommended ([protobuf-conformance README](https://github.com/bufbuild/protobuf-conformance/blob/main/README.md)). Peers have set the bar there. Protobuf-ES, protobuf.js and buffa all report zero required failures, and buffa's README claims "zero expected failures" while keeping a separate list for each codec mode ([buffa README](https://github.com/anthropics/buffa/blob/main/README.md)). RustPB will *not* have an empty list, because matching ScalaPB requires deliberate deviations. So it must explain each one, not hide it. It should publish six things, all produced by `harness/report` from CI artifacts:

| Artifact | Contents | Why it earns trust |
|---|---|---|
| `docs/TESTING.md` ("How RustPB is tested") | Each oracle with counts; fixture and corpus sizes per rule ID; fuzz targets and CPU hours; tier budgets; mutation results with each survivor justified; line and region coverage; Kani harnesses with their bounds; a "what we do not test" section; last-updated date | One page a skeptic can audit |
| Results matrix | Rows are fixtures and conformance tests; columns are rustpb native, rustpb on Node, rustpb on Bun, ScalaPB, and prost and buffa for context; `i_` rows highlighted | The equivalence claim made visible, case by case |
| Failure lists with counts | `scalapb`, `native` and `js` lists, each line with its reason or ADR; README badges; the three-way equality shown | Deviations are documented by the suite itself |
| Compatibility promise | Three promises, each tied to a test: wire and JSON equality with named ScalaPB and jsoniter versions (golden corpus and differential); Rust API semver (cargo-semver-checks); skew between generated code and runtime (an old-generated-code compile check plus a version-enforcing constant, protobuf-go style) | States what may break and what catches it |
| Size and speed | Bundle sizes measured with protobuf-es's method (esbuild, minify, compress) beside protobuf-es itself; a speed trend, not a gate | Answers the obvious comparison honestly |
| Hygiene | SECURITY.md, pinned actions, `cargo deny` and `cargo audit`, release provenance, ClusterFuzzLite listing | Machine-checkable signals (OpenSSF Scorecard, Best Practices) |

Two claims must be avoided. MC/DC: rustc **removed all MC/DC instrumentation in August 2025** ([rust-lang/rust#144999](https://github.com/rust-lang/rust/pull/144999)), and re-implementing it is only a 2026 project-goal proposal. Coverage is therefore a gap-finder, and mutation testing is the stronger signal. "Proven" for JS output: Kani proves the Rust, and the numbers grid tests the emitted JS. The protobuf-go compatibility section is the model for wording. It lists the exact permitted breaks and promises 6 months' notice for anything else ([protobuf-go README](https://github.com/protocolbuffers/protobuf-go/blob/HEAD/README.md)).

Several questions stay open, and the harness exists to close them. Nobody knows which conformance tests jsoniter 0.1.2 passes until the worker runs under the runner. ScalaPB's recursion limit and its ten-byte varint rule are unverified until the boundary fixtures are recorded. The design's open question 3, `BTreeSet` against `HashSet`, never yields byte equality with Scala's hash-ordered `Set`, so sets are always compared canonically whichever way it is decided. And the notes give no throughput figure for a framed-pipe JVM worker, only spawn and JNI figures. The first measurement belongs in `TESTING.md`.

## Conclusion

The research changes what "oracle" means for RustPB. The design ranks its oracles by authority: ScalaPB primary, conformance secondary. The harness has to rank them by *where they run*. ScalaPB is the authority, but it is slow and external, so its judgement must be captured as data once and replayed everywhere, re-asked only when the oracle or the case changes. Google's runner then stops being a second opinion on correctness. It becomes an instrument that measures the authority itself, and it is the only way to see deviations ScalaPB and RustPB share. The native-against-JS axis, which the design schedules last, is the one rust-js's own history says finds the most wrong answers, so it belongs from the first milestone. And the riskiest code, the generator, needs generated schemas, because nothing written by hand reaches the combinations of 7,785 mapped fields.

The trust argument follows from that. A new protobuf library is now judged by a number on a badge, and RustPB's number cannot be zero, because faithfulness to ScalaPB requires deliberate deviations. Its credibility will rest on making each deviation *measured rather than asserted*. The list RustPB publishes is the list ScalaPB itself produces under the same runner. Every fixture carries the oracle version that recorded it. The testing page is generated by the suite it describes. A project that shows where it differs, why, and the run that proves it, earns more trust than one that claims a clean sheet.
