## 1. Differential fuzzing architectures in practice (oracle hosting, throughput, determinism, timeouts, triage)

### Takeaway
No surveyed project fuzzes a Rust protobuf library against another language's protobuf library; the Rust protobuf crates (prost, buffa) fuzz only against themselves (round-trip and size invariants), and upb's only cross-implementation fuzzers are in-process C vs C++. Cross-language differential fuzzers that worked in practice host the slow foreign oracle **in-process (JNI / FFI static library)** or as a **long-lived warm process**; spawning a fresh JVM per input is 100x too slow. The protobuf conformance runner's framed stdin/stdout protocol already exists and ScalaPB already implements a testee for it.

### Cited Findings

**Protobuf ecosystem (local source)**
- prost's fuzz targets (`fuzz/fuzzers/proto3.rs`, `proto2.rs`) decode raw bytes into `TestAllTypesProto3/2` and call `tests::roundtrip`, which checks `encoded_len() == bytes written`, that the re-encoded bytes decode, and that `encode` and `encode_to_vec` of the re-decoded value both equal the first re-encoding (`buf1 == buf2`, `buf1 == buf3`). A TODO notes the check `encoded_len <= data.len()` is disabled "once sign-extension in negative int32s is figured out" — `~/Documents/GitHub/prost/tests/src/lib.rs:156-215`. Two more targets fuzz `Timestamp`/`Duration` string parsing, the date one differentially against `chrono::DateTime::parse_from_rfc3339`, with explicit carve-outs (leap seconds, years 0000–9999) — `~/Documents/GitHub/prost/fuzz/fuzzers/parse_date.rs`.
- prost runs CIFuzz on every pull request using its OSS-Fuzz project (`oss-fuzz-project-name: 'prost'`, `fuzz-seconds: 300`, crash artifacts uploaded on failure) — `~/Documents/GitHub/prost/.github/workflows/cifuzz.yml`. prost also keeps an AFL target with a seed corpus (`fuzz/afl/proto3/in/{empty,testmessage}`) — `~/Documents/GitHub/prost/fuzz/afl/proto3/README.md`.
- prost's regression fixtures from fuzzing are hand-pasted byte arrays in a unit test ("Some selected encoded messages, mostly collected from failed fuzz runs") — `~/Documents/GitHub/prost/tests/src/lib.rs:263-273`.
- buffa has 6 targets: binary decode (proto2, proto3, WKT), binary encode from `Arbitrary` messages, JSON round-trip, and WKT JSON string parsers — `~/Documents/GitHub/buffa/fuzz/Cargo.toml`, `~/Documents/GitHub/buffa/CHANGELOG.md:1916`. Its round-trip oracle deliberately does **not** compare messages with `PartialEq` or bytes across map fields, because of `HashMap` order and `NaN != NaN`; it compares via `serde_json::Value` (BTreeMap keys) instead — `~/Documents/GitHub/buffa/fuzz/src/lib.rs`, `~/Documents/GitHub/buffa/fuzz/fuzzers/json_roundtrip.rs`.
- buffa's `encode_proto3` target bails out when `compute_size() > 65_536`, because `Arbitrary` can turn a few input bytes into megabyte buffers and the JSON `Value` tree is "10-50x the wire size"; at 1 MB they "hit the 2GB rss limit after ~1.6M iterations (Mar 2026, oom-f1a736fc)" under ASan, and 64 KB is "sustainable for 14hr runs". It also treats `RecursionLimitExceeded` on its own output as expected — `~/Documents/GitHub/buffa/fuzz/fuzzers/encode_proto3.rs`.
- buffa's `wkt_json_strings` target exists because byte-level mutation of whole JSON documents essentially never reaches the Timestamp/Duration/FieldMask string parsers ("the probability of finding `"2024-02-30T25:61:61Z"` by byte mutation is essentially zero"), so it feeds the fuzz string directly into each WKT's `Deserialize` — `~/Documents/GitHub/buffa/fuzz/fuzzers/wkt_json_strings.rs`.
- protobuf-go's `wirefuzz` is an internal differential oracle: the fast unmarshaler and the separate `impl.Validate` must agree on validity and on "initialized"; then Marshal → `proto.Size == len` → Unmarshal → `proto.Equal`. The committed corpus runs as an ordinary `go test` (`fuzztest.Test` iterates the corpus directory) — `~/Documents/GitHub/protobuf-go/internal/fuzz/wirefuzz/fuzz.go`, `~/Documents/GitHub/protobuf-go/internal/fuzztest/fuzztest.go`. Its `jsonfuzz` returns 0 (not a failure) when the *re-parse of its own JSON output* fails — `~/Documents/GitHub/protobuf-go/internal/fuzz/jsonfuzz/fuzz.go`.
- upb has true differential fuzzers, in-process: `compare_fuzz_test.cc` checks `upb_Message_IsEqual(..., PARTIAL)` against C++ `MessageDifferencer` with `PARTIAL` scope on scalars, maps and extensions — `upb/message/compare_fuzz_test.cc` in `~/Documents/GitHub/protobuf` (read via `git show HEAD:`). upb uses Google's FuzzTest (`FUZZ_TEST(...)`) — same files.
- The conformance protocol: "the suite will send a ConformanceRequest message and expect a ConformanceResponse", either in-process or "as a sub-process communicating over a pipe", the latter being "much simpler for languages other than C/C++" — `conformance/conformance.proto` in `~/Documents/GitHub/protobuf`. ScalaPB's testee reads a 4-byte little-endian length then the request from stdin and writes the same framing to stdout; it uses scalapb-json4s for JSON, and ScalaPB keeps a 19-line binary/JSON failure list and a 31-line text-format failure list — `~/Documents/GitHub/ScalaPB/conformance/src/main/scala/ConformanceScala.scala`, `~/Documents/GitHub/ScalaPB/conformance/*.txt`. ScalaPB's runner build script pins protobuf 3.19.6 — `~/Documents/GitHub/ScalaPB/conformance/build_test_runner.sh`.

**Cross-language oracle hosting (other domains)**
- beacon-fuzz (maintained by Sigma Prime) differentially fuzzed Ethereum consensus clients in Rust, Go, Java, Nim and JS. The Java client (Teku) ran in an **in-process JVM started from native code and called via JNI**; Go clients were built as static libraries behind an FFI (`go-bfuzz-build`), because go-fuzz does not support cgo. Engines: AFL++, honggfuzz, libFuzzer; structured inputs via `Arbitrary` — [beacon-fuzz README](https://github.com/sigp/beacon-fuzz); [Beacon Fuzz update #03](https://blog.sigmaprime.io/beacon-fuzz-03.html); [update #04](https://blog.sigmaprime.io/beacon-fuzz-04.html). (Sources describe the 2020–2021 era.)
- A Dec 2025 cross-language EVM differential fuzzer (Go, Java, C#) measured per-input cost as a **subprocess: ~2.18 s (.NET) and ~3.03 s (Java) vs ~21.5 ms (Go binary)** and rejected it. Java was moved **in-process via the Rust `jni` crate**: ~2.6 s first call, then single-digit ms after warm-up. .NET embedding (Native AOT, netcorehost) failed; the working fallback was a **long-running process exchanging inputs through `/dev/shm` with START/DONE flags** (~6–15 ms per call), which needed a separate signal segment to avoid races. Coverage feedback came from only one implementation (Go, via a LibAFL shim) — [Differential Fuzzing Across The Language Divide](https://r9295.github.io/posts/differential-fuzzing-accross-languages).
- Jazzer is "a coverage-guided, in-process fuzzer for the JVM" based on libFuzzer, instrumenting bytecode so any JVM language works; its maintainers list "inconsistent implementations (differential fuzzing)" as a target bug class — [Code Intelligence blog](https://www.code-intelligence.com/blog/fuzz-targets-jazzer); [Google Security Blog, Fuzzing Java in OSS-Fuzz (2021)](https://security.googleblog.com/2021/03/fuzzing-java-in-oss-fuzz.html?m=1). No source found showing Jazzer paired with a Rust oracle.

**Compilers and engines (Rust)**
- wasmtime's `differential` target generates a module (wasm-smith or a single-instruction generator), instantiates it in a chosen engine and in Wasmtime, calls each export with random arguments, and compares results; engines are selected with `ALLOWED_ENGINES=wasmi,pulley` / `ALLOWED_ENGINES=-v8`, module kinds with `ALLOWED_MODULES`. Exports whose signature an engine can't call are skipped; once the two instances' state diverges, execution stops. It keeps counters of what actually ran (inputs, invocations, completed runs, engine and module choice) — `~/Documents/GitHub/wasmtime/fuzz/fuzz_targets/differential.rs`. The `DiffEngine` trait has `assert_error_match(err, trap)` and `is_non_deterministic_error(err)` (stack overflow, too-large allocation) to classify errors — `~/Documents/GitHub/wasmtime/crates/fuzzing/src/oracles/engine.rs`. NaNs are canonicalized "so we can paper over NaN differences between engines" — `~/Documents/GitHub/wasmtime/crates/fuzzing/src/generators/config.rs:69-71`.
- The current wasmtime tree has oracles `diff_v8.rs`, `diff_wasmi.rs`, `diff_wasmtime.rs` and **no `diff_spec.rs`** — `~/Documents/GitHub/wasmtime/crates/fuzzing/src/oracles/`. An issue proposed removing the spec-interpreter oracle because no differential issues had been found with it in years and wasmi had matched its feature coverage — [wasmtime #13561 (mirror)](https://gh.r-mj.com/bytecodealliance/wasmtime/issues/13561). V8 was added (PR #3264, 2021) because the spec interpreter was too slow for fuzzing; V8 has no fuel/timeout, so inputs must not loop forever — [Zulip archive of PR #3264](https://bytecodealliance.github.io/zulip-archive/stream/225357-git-wasmtime/topic/wasmtime.20.2F.20PR.20.233264.20Add.20differential.20fuzzing.20against.20V8.html).
- cranelift-fuzzgen compares Cranelift's interpreter with compiled code: it generates several inputs per compiled function "since compilation may be expensive", rebuilds the interpreter every run "so that we don't accidentally carry over any state between runs, such as fuel remaining", skips inputs that trap, and collects statistics on timeouts and trap codes — `~/Documents/GitHub/wasmtime/fuzz/fuzz_targets/cranelift-fuzzgen.rs`.
- Csmith reported more than 325 compiler bugs over about three years; YARPGen over 220 bugs in GCC, LLVM and the Intel compiler, including bugs Csmith could not find; compilers become resistant to a fixed generator over time — [YARPGen OOPSLA'20](https://users.cs.utah.edu/~regehr/yarpgen-oopsla20.pdf); [CsmithEdge, EMSE 2022](https://link.springer.com/article/10.1007/s10664-022-10146-1). Test-case reducers must reject reduced variants that introduce undefined behavior or infinite loops (the "interestingness test") — [Regehr blog](https://blog.regehr.org/archives/1069).

**Parser differentials and triage**
- A 2021 survey of 49 JSON parsers found every language had at least one parser with risky interoperability behavior: inconsistent duplicate-key precedence, large numbers converted to strings like `+Infinity`, etc. — [An Exploration of JSON Interoperability Vulnerabilities](https://bishopfox.com/blog/json-interoperability-vulnerabilities).
- By construction, differential testing cannot see non-compliances shared by all implementations (inference; the VUPER paper, arXiv 2608.09094, was checked and does not state this). A 2026 paper reports most findings in a typical differential run are not actionable bugs, making triage the bottleneck — [SmartOracle, arXiv 2601.15074](https://arxiv.org/pdf/2601.15074).

### Inferences
- **Oracle hosting for RustPB.** Per-input JVM spawn (~seconds) is unusable. Two viable designs: (a) **long-lived ScalaPB worker process** speaking the conformance framing (4-byte LE length + payload) over stdin/stdout, batched; (b) **JNI in-process** (beacon-fuzz / `jni` crate), which gives ms-level latency but couples a JVM's signal handlers, GC threads and memory to libFuzzer's process (ASan + JVM is a known-awkward pairing; not verified here). Inference: (a) is simpler, isolates JVM crashes and hangs, and reuses an existing ScalaPB testee; batching N inputs per frame amortizes pipe latency. The same framed worker works for the JS build (one long-lived Bun/Node process loading rust-js output).
- **Decouple coverage-guided search from the oracle.** The EVM fuzzer took coverage from one implementation only. For RustPB: run libFuzzer on the Rust side only (fast, coverage of the Rust decoder), with single-sided oracles in-loop (no panic, size == written, re-encode stable, JS-shaped checks), and **send the growing corpus to ScalaPB and JS in batches** (corpus replay) rather than per execution. This keeps execs/sec high and makes the cross-language comparison deterministic and replayable.
- **Compare a canonical outcome record**, not raw objects: `{ok: canonical-bytes + canonical-JSON + value-dump} | {err: class}`. Canonicalize what the design (§4.6, §6) already says is non-deterministic: unknown-field order across numbers (ScalaPB uses a Scala hash map), map entry order, NaN payloads. Like wasmtime's `is_non_deterministic_error`, classify resource errors (depth, size limits) separately from semantic disagreement, and compare error *classes*, not messages, unless messages are part of the contract.
- Timeouts: a JVM worker needs a watchdog (kill + restart + record input as a hang); V8's lack of fuel is the cautionary example.
- Keep statistics in the harness (wasmtime and cranelift-fuzzgen do) — the fraction of inputs that decode successfully on both sides is the key health metric; a raw-byte fuzzer whose inputs almost all fail decode is mostly testing the error path.

### Gaps
- No published example found of fuzzing a Rust implementation against a JVM *serialization* library specifically, nor throughput numbers for a framed-pipe JVM worker (only per-spawn and JNI numbers).
- No source found on running JNI-hosted JVMs under ASan/libFuzzer reliably; beacon-fuzz posts don't detail problems.
- No public evidence of protobuf-go vs C++ cross-implementation fuzzing (only protobuf-go's internal fast-path-vs-validator differential).

## 2. Structure-aware fuzzing for protobuf (libprotobuf-mutator, arbitrary, bolero, schema generators, dictionaries)

### Takeaway
Two complementary input sources are standard: raw-byte mutation of valid encodings (finds decoder edge cases) and typed generation (`Arbitrary` messages → encode; finds encoder/size/round-trip bugs). Random **schema** generation exists in upb (random MiniDescriptors), not in any Rust crate found. libprotobuf-mutator is C++ only; Rust's equivalent is `fuzz_mutator!` + mutatis.

### Cited Findings
- libprotobuf-mutator is a C++ library that randomly mutates protobuf messages for use with guided engines like libFuzzer; it needs Protobuf ≥3.6.1.3 and Clang ≥12 — [libprotobuf-mutator README](https://chromium.googlesource.com/external/github.com/google/libprotobuf-mutator/+show/HEAD/README.md). Chromium notes grammar fuzzers with it "require greater effort" than plain libFuzzer — [Chromium libprotobuf-mutator doc](https://chromium.googlesource.com/chromium/src/+/main/testing/libfuzzer/libprotobuf-mutator.md). No maintained Rust binding was found (search, 2026-11-13).
- **Random schemas: upb.** `MiniTableFuzzInput` carries N random message MiniDescriptors, N enum MiniDescriptors, extension descriptors and integer "links" taken modulo the count "so that any link value can be valid"; `BuildMiniTable` turns it into a schema at fuzz time — `upb/test/fuzz_util.h` in `~/Documents/GitHub/protobuf`. `ConvertFuzz(const MiniTableFuzzInput&, mask1, ...)` is a `FUZZ_TEST` over such random schemas, and fuzzer findings are pinned as named `TEST`s with literal inputs (e.g. `Regression_FuzzerFinding_UnknownFields`, `ManualUnknownFieldRepro`) — `upb/message/convert_fuzz_test.cc:101-226`. upb's `def_to_proto_fuzz_test.cc` fuzzes descriptor round-trips — file list in the same repo.
- No tool was found that generates random `.proto` files for cross-implementation differential testing; nearest are tools that scan given schemas or mutate messages against a fixed schema — [search summary incl. pbtk](https://github.com/marin-m/pbtk).
- protobuf-go uses a dedicated fuzz schema (`internal/testprotos/fuzz/fuzz.proto`) and an editions fuzz schema — `~/Documents/GitHub/protobuf-go/internal/testprotos/`.
- buffa derives `Arbitrary` for generated messages behind an `arbitrary` feature ("`arbitrary::Arbitrary` impls for fuzzing") and uses `fuzz_target!(|msg: TestAllTypesProto3| ...)` for its encode target — `~/Documents/GitHub/buffa/buffa/src/lib.rs:88`, `~/Documents/GitHub/buffa/fuzz/fuzzers/encode_proto3.rs`.
- `fuzz_target!` accepts any `Arbitrary` type; `fuzz_mutator!` defines custom mutators over corpus entries (example: decompress → `fuzzer_mutate` → recompress), and the rust-fuzz book reports mutator-based fuzzing reached better coverage over time than `Arbitrary`-based generation in its example; mutatis helps write mutators (`derive(Mutate)`, `Session` with seed and shrink) — [Rust Fuzz Book](https://rust-fuzz.github.io/book/print.html).
- wasmtime uses `fuzz_mutator!` with wasm-mutate (structure-preserving mutations of valid modules) and clamps `max_size` to `len * 2` per mutation to avoid over-allocation — `~/Documents/GitHub/wasmtime/crates/fuzzing/src/mutators.rs`.
- bolero is a front end over libFuzzer (default), AFL, honggfuzz and Kani (`cargo bolero test --engine kani`), with `TypeGenerator` derive for structured inputs; the same harness also runs as a property test — [bolero book](https://camshaft.github.io/bolero/print.html); [Kani + bolero post (2022)](https://model-checking.github.io/kani-verifier-blog/2022/10/27/using-kani-with-the-bolero-property-testing-framework.html). fuzzcheck is a structure-aware engine that avoids an intermediate encoding — [fuzzcheck docs](https://docs.rs/crate/fuzzcheck/latest).
- Google FuzzTest (used by upb): by default `FUZZ_TEST`s run "with random inputs for a short time" as unit tests without instrumentation; fuzzing mode (`--fuzz=`) runs coverage-guided until a crash — [FuzzTest quickstart](https://github.com/google/fuzztest/blob/main/doc/quickstart-cmake.md).

### Inferences
- For RustPB, a three-layer input strategy follows from the evidence:
  1. **Raw bytes** seeded from valid encodings (golden corpus from ScalaPB, §6.1) + a libFuzzer dictionary of tag bytes for the test schema's field numbers × wire types, `0x80`-continuation varint fragments, 10-byte max varints, and zigzag extremes. (Dictionary content is inference; libFuzzer's `-dict` is standard.)
  2. **Typed messages** via `Arbitrary` derived on generated types (buffa's way) → encode → feed both encoders/decoders; cap encoded size (buffa's 64 KB lesson).
  3. **Structure-aware mutation** via `fuzz_mutator!`: decode → mutate fields → re-encode, plus wire-level edits that keep framing valid (insert unknown field, duplicate a field, split packed runs, swap wire type) — this reaches the §6.4 fixture classes far more often than raw bytes.
- **Random schemas** are the biggest gap: RustPB's real risk is in codegen (mappers, oneofs, options), which a single fixed `TestAllTypes` schema can't exercise. upb shows the pattern (schema from fuzz bytes, links modulo count). For RustPB this means a generator that emits a random `.proto` (with `(rustpb.field)`/ScalaPB options), runs both code generators, compiles both, and runs random messages through both — a slow outer loop (minutes per schema) suited to nightly runs, Csmith-style, rather than libFuzzer.
- JSON needs its own targets: whole-document byte mutation rarely reaches WKT string parsers (buffa), so add per-scalar-format targets (int64-as-string, float `"NaN"`/`"-Infinity"`, Timestamp, Duration, FieldMask, base64 bytes) and differential-compare them with scalapb-jsoniter.

### Gaps
- No Rust libprotobuf-mutator equivalent driven by `.proto` descriptors was found; would need to be built (prost-reflect `DynamicMessage` + mutatis is one plausible base — unverified).
- No published random `.proto` schema generator used for cross-language differential testing found.

## 3. Rust fuzzing tooling: engines, corpus management, coverage, CI budgets, OSS-Fuzz

### Takeaway
cargo-fuzz/libFuzzer is the de-facto standard (OSS-Fuzz's only engine for Rust); AFL (afl.rs) and honggfuzz are alternatives, unified by bolero or ziggy. CI fuzzing norms: 5–10 min per PR (prost uses 300 s; ClusterFuzzLite default 600 s), longer scheduled batch runs with daily corpus pruning, and coverage reports from the batch corpus.

### Cited Findings
- cargo-fuzz: `init`, `add`, `build`, `run`, `list`; args after `--` go to libFuzzer (`-max_total_time=`); every crate is built with `--cfg fuzzing`; crashes go to `fuzz/artifacts/<target>/crash-<hash>`; `cargo fuzz coverage <target> [corpus]` builds with `-Cinstrument-coverage`, replays the corpus and merges into `coverage.profdata` (needs cargo-fuzz ≥0.10 and `llvm-tools-preview`). afl.rs: `cargo afl build`, `cargo afl fuzz -i in -o out`, needs ≥1 seed, a panic inside `fuzz!` aborts so AFL records a crash — [Rust Fuzz Book](https://rust-fuzz.github.io/book/print.html).
- OSS-Fuzz Rust: base image `gcr.io/oss-fuzz-base/base-builder-rust` (nightly + cargo fuzz), `language: rust`, sanitizer `address` only, engine `libfuzzer` only, build with `cargo fuzz build -O` (optionally `--debug-assertions`), copy binaries to `$OUT`; fuzz-only deps under `[target.'cfg(fuzzing)'.dependencies]` — [OSS-Fuzz Rust guide](https://google.github.io/oss-fuzz/getting-started/new-project-guide/rust-lang/).
- OSS-Fuzz acceptance: the project "must have a significant user base and/or be critical to the global IT infrastructure"; the primary contact must be an established committer (checked against VCS) with a Google-account-linked email — [Accepting new projects](https://google.github.io/oss-fuzz/getting-started/accepting-new-projects/).
- ClusterFuzzLite modes: `code-change` (default; runs only fuzzers affected per coverage data, else all; stops at first crash), `batch` (all fuzzers, longer, reports all crashes, builds corpus), `prune` (mandatory daily with batch), `coverage` (HTML report from batch corpus). Default `fuzz-seconds` is 600 s; increase for batch; "continuous builds" let code-change tell whether a crash is new — [Running ClusterFuzzLite](https://google.github.io/clusterfuzzlite/running-clusterfuzzlite).
- prost's CIFuzz runs 300 s per PR — `~/Documents/GitHub/prost/.github/workflows/cifuzz.yml`. buffa's fuzz crate is excluded from the workspace ("requires nightly and libfuzzer") and its CI workflow contains no fuzz job — `~/Documents/GitHub/buffa/fuzz/Cargo.toml`; grep of `~/Documents/GitHub/buffa/.github/workflows/`.
- protobuf-go runs its committed fuzz corpus as normal unit tests on every `go test` — `~/Documents/GitHub/protobuf-go/internal/fuzztest/fuzztest.go`. FuzzTest runs fuzz tests briefly in unit-test mode by default — [FuzzTest quickstart](https://github.com/google/fuzztest/blob/main/doc/quickstart-cmake.md).

### Inferences
- RustPB is new and will not meet OSS-Fuzz's user-base bar initially; ClusterFuzzLite on GitHub Actions gives the same modes self-hosted. Suggested split (inference): PR = code-change 300–600 s on Rust-only single-sided targets + **replay of the full regression corpus through all three implementations** (deterministic, fast); nightly = batch fuzzing + prune + coverage + cross-language replay of the new corpus + random-schema campaigns.
- Because the cross-language comparison is replay-based, a PR's differential check is deterministic and cheap, and fuzzing time only buys new inputs. This avoids flaky PR results tied to time-boxed fuzzing.
- Use `cargo fuzz coverage` on the merged corpus to find unreached decoder branches (e.g. group skipping, depth limits), and add seeds or mutators for them.
- The JS build cannot be fuzzed coverage-guided via libFuzzer; corpus replay through a long-lived JS worker is the realistic way (inference; Jazzer.js exists but was not researched here).

### Gaps
- No public numbers found on execs/sec for protobuf decoders under cargo-fuzz.
- Didn't verify libFuzzer flag defaults (`-rss_limit_mb`, `-timeout`, `-max_len`) from primary docs in this pass.

## 4. Mutation testing in Rust (cargo-mutants)

### Takeaway
cargo-mutants (27.1.0) is the standard Rust mutation tester. It classifies mutants as caught / missed / unviable / timeout, supports diff-scoped runs and sharding, and its author recommends treating misses as missing behavioral tests, not as a score target.

### Cited Findings
- Outcomes: caught, missed ("coverage gap or an equivalent mutant"), unviable (doesn't compile), timeout. Only missed and timeouts are printed by default — [cargo-mutants book](https://mutants.rs/print.html).
- Triage guidance: look first for surprising misses and clusters; write tests for the public behavior the mutant breaks, avoid tests "too tightly targeted to the mutant"; equivalent mutants → `#[mutants::skip]` or `#[mutants::exclude_re("…")]`; config filters in `.cargo/mutants.toml` (`exclude_re`, `exclude_globs`); `--list` to preview — [cargo-mutants book](https://mutants.rs/print.html).
- Incremental: `--in-diff DIFF_FILE` tests mutants overlapping a diff and is "not a substitute for a full test run"; `--iterate` skips previously caught/unviable mutants — [in-diff](https://mutants.rs/in-diff.html); [iterate](https://mutants.rs/iterate.html); [PR diff](https://mutants.rs/pr-diff.html).
- Sharding: `--shard k/n` with identical args across shards, "8 to 32 shards" suggested, `--baseline=skip` on shards if the baseline is checked elsewhere; each shard uploads its own `mutants.out` — [shards](https://mutants.rs/shards.html).
- Default test timeout: 5× baseline test time, minimum 20 s; `--test-tool=nextest` supported but nextest skips doctests, so doctest-only catches show as missed — [cargo-mutants book](https://mutants.rs/print.html).
- No target score is recommended; "Most, ideally all, findings should indicate something that really should be tested more"; for well-tested trees use it in CI to keep them that way — [cargo-mutants book](https://mutants.rs/print.html).
- One project's published policy: non-blocking `--in-diff` on every PR, capped full sharded runs, auto-created triage issues with a 7-day SLA — [ECMWF tensogram mutation-testing page](https://sites.ecmwf.int/docs/tensogram/main/dev/mutation-testing.html) (project-specific example).

### Inferences
- cargo-mutants' built-in mutation operators (replace fn body with default, flip operators) cover runtime crates; RustPB's design §6.5 also needs **codegen-level mutations** (swap a tag, drop zigzag, skip an unknown field) that cargo-mutants cannot express since they live in generated code. Those need a small custom mutation list run against the corpus/fixture suite (as rust-js does with its own mutations script).
- A useful gate: every mutant in the wire/JSON runtime is either caught or carries a written `exclude_re` justification; `--in-diff` blocking on PRs touching the runtime.

### Gaps
- Didn't find published mutation scores or survivor-triage write-ups from protobuf crates (prost, buffa) — none appear to run cargo-mutants (no config found in local clones; not exhaustively verified).

## 5. Regression discipline: every fuzz finding becomes a permanent fixture; seeding from advisories

### Takeaway
Mature projects pin each fuzzer finding as a named, literal-input unit test (upb, prost) and run the whole committed corpus as an ordinary test (protobuf-go); none of the Rust protobuf crates was found to seed corpora from RUSTSEC advisories systematically.

### Cited Findings
- upb: findings become named `TEST`s calling the fuzz function with literal inputs (`Regression_FuzzerFinding_UnknownFields`, `ManualUnknownFieldRepro`) next to the `FUZZ_TEST` — `upb/message/convert_fuzz_test.cc:176-226` in `~/Documents/GitHub/protobuf`.
- prost: a unit test holds byte arrays "mostly collected from failed fuzz runs" and runs them through the same round-trip oracle — `~/Documents/GitHub/prost/tests/src/lib.rs:263-273`.
- protobuf-go: the committed corpus directory is replayed by `go test` (sorted, one subtest per file, capacity trimmed to length so out-of-bounds appends are caught) — `~/Documents/GitHub/protobuf-go/internal/fuzztest/fuzztest.go`.
- ClusterFuzzLite's `prune` keeps the corpus minimal and the batch corpus seeds later code-change runs; without one, runs start from the seed corpus or empty — [Running ClusterFuzzLite](https://google.github.io/clusterfuzzlite/running-clusterfuzzlite).
- upb copies JSON fuzz input to the heap "This helps asan reproduce issues that don't reproduce when passing static memory pointers" — `upb/json/fuzz_test.cc` in `~/Documents/GitHub/protobuf`.

### Inferences
- For RustPB, a finding should land as three artifacts in one commit: (1) the minimized input in a `fixtures/` directory with ScalaPB's recorded outcome (bytes/JSON/error class) as the expected file, (2) the input copied into each fuzz target's seed corpus, (3) a named test (`regression_<issue>`) replayed by native, ScalaPB and JS runners. Recording ScalaPB's answer at fixture time means PR CI doesn't need a JVM for regressions, while the nightly re-checks the recorded answers against a live ScalaPB to catch oracle-version drift.
- Minimization must preserve "the same disagreement", not just "a failure": use an interestingness predicate that compares the outcome pair (as C-Reduce's interestingness tests do), or a reduced input may flip into a different, unrelated disagreement. libFuzzer's `-minimize_crash` / `cargo fuzz tmin` minimize for any crash only (behavior inferred from libFuzzer docs, not verified this pass).
- Advisory seeds: one input per RUSTSEC/GHSA protobuf advisory (depth bombs, huge declared lengths, group recursion) as design §4.6 lists; pin them as named tests with the advisory ID.
- Track the oracle version: ScalaPB / scalapb-jsoniter versions are part of each fixture's provenance; an oracle upgrade re-records and diffs all fixtures.

### Gaps
- No written policy from prost or buffa on converting fuzz crashes into fixtures was found beyond the code itself.
- No public corpus of protobuf advisory reproducers was found; it would have to be assembled from each advisory's linked issue.
