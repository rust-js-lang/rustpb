# Rust's protobuf history hardens RustPB's design

> **Reviewed revision.** This report reviewed `docs/design.md` at `297e067`. Its statements about what "the design" says or lacks, and its findings table, describe that revision as a historical baseline; later revisions resolved most of them (current status: `docs/design.md`). Factual claims about other projects are kept current.

No Rust protobuf project ships what RustPB promises. None combines a per-field semantic type mapper, unknown-field preservation, ScalaPB-shaped sealed oneofs, implementation-exact proto3 JSON and a runtime simple enough to compile to JavaScript. So RustPB's headline features are novel, and RustPB must own their correctness alone. The existing projects still teach a great deal, mostly through their failures. Every RustSec advisory against a Rust protobuf crate is a denial of service through an unbounded path: recursion through unknown groups, or an allocation sized by an attacker's length prefix. The byte-level bugs that survived longest sit where RustPB is most exposed. prost wrote proto3 repeated fields unpacked whenever the field carried *any* option, the exact shape of RustPB's 7,785 option-annotated fields. Maps accepted the wrong wire type until November 2026, and a size computation disagreed with the writer for negative enum values. In JSON, every crate that leans on serde's defaults leaks non-protobuf behaviour: NaN becomes `null`, timestamps get `+00:00`, enum aliases are lost. The design doc already follows the most important lessons: a fallible mapper that is its own type, unknown fields in the struct by default, a real `Unrecognized` enum variant, cycle-safe default construction, and explicit serde impls. Nine high-priority lessons are absent from it, though, and three places quietly inherit prost behaviour that may diverge from ScalaPB. The prioritized table at the end lists them by design-doc section.

## Nobody in Rust ships ScalaPB's hard features together

The landscape in November 2026 is a vacuum with one fast-moving exception.

**prost**, the de facto standard, is now "passively maintained". The current maintainer is "not contributing new features" and expects users to move to Google's crate ([prost README](https://github.com/tokio-rs/prost/blob/v0.14.6/README.md)). It has:

- no unknown fields: [#2](https://github.com/tokio-rs/prost/issues/2), open since 2017. An opt-in PR has waited since 2025 because "I have limited time and energy for prost" ([PR #1340](https://github.com/tokio-rs/prost/pull/1340)).
- no JSON: [#75](https://github.com/tokio-rs/prost/issues/75), open since 2018.
- no per-field custom types. Requests for them have been open since 2021, and a "mini-RFC" stated the right principle that was never built: wrappers "should be transparent wrt the wire format" ([#427](https://github.com/tokio-rs/prost/issues/427), [#764](https://github.com/tokio-rs/prost/issues/764)).

prost's only type-substitution seam, `extern_path`, swaps whole *message* types, and the substitute must implement `Message`. A maintainer closed a scalar-mapping request saying it "doesn't fit prost well. We aim to be a Rust equivalent of the C++ protobuf library" ([#448](https://github.com/tokio-rs/prost/issues/448)).

**rust-protobuf** is "approaching end of life" ([README](https://github.com/stepancheg/rust-protobuf/blob/0118c79e51c8d54ac40deb8b82631ddef81fb00e/README.md)). Its maintainer answered a request to map a field exactly as `(scalapb.field).type` does with "There's no way to do that now". The user "finally solved it with prost" ([#552](https://github.com/stepancheg/rust-protobuf/issues/552)).

**Google's official crate** (`protobuf` 4.x, now renamed `google-protobuf` 0.x) is still beta. It compiles upb's C sources through `cc` ([build.rs](https://github.com/protocolbuffers/protobuf/blob/8e2636c3aaeedc3cd22963814e7727564a017bfc/rust/release_crates/google_protobuf/build.rs)), has no JSON ("Rust proto is only supporting lite.api today", [#24938](https://github.com/protocolbuffers/protobuf/issues/24938)), and exposes opaque `View`/`Mut` proxies instead of plain structs ([design decisions](https://protobuf.dev/reference/rust/rust-design-decisions/)). Those are reasonable choices for C++/Rust interop, and they rule the crate out as a source for Rust-to-JS compilation.

**buffa** is the exception, and the most important prior art. It is pure Rust, keeps unknown fields by default, has open-enum wrappers, and passes the binary and JSON conformance suites with empty failure lists ([buffa README](https://github.com/anthropics/buffa/blob/main/README.md)). Its knobs (`string_type`, `bytes_type` and similar) swap *representation* only, though. Semantic scalar mapping is an open, maintainer-endorsed proposal ([buffa #490](https://github.com/anthropics/buffa/issues/490)), and that proposal's adapter is **infallible**. Other projects fill only niches:

- gin-tonic has the closest ScalaPB analogue: a `(gin_tonic.v1.rust_type)` option plus a fallible `Scalar<ProtoType>` trait ([traits.rs](https://codeberg.org/cemoktra/gin-tonic/src/commit/e31fae4f1f63811b119c3efac805f10a85c600f5/core/src/traits.rs#L3-L23)).
- pilota's `rust_type` accepts four hard-coded strings ([resolve.rs](https://github.com/cloudwego/pilota/blob/8239e1e20b/pilota-build/src/resolve.rs#L290-L330)).
- micropb's `custom_field` hands raw wire handling to user code ([config.rs](https://github.com/YuhanLiin/micropb/blob/0b86edac8e/micropb-gen/src/config.rs#L59-L83)).

| Project | Field-level semantic mapping | Unknown fields | Enum model | JSON | Viable for Rust→JS |
|---|---|---|---|---|---|
| prost 0.14 | No (message-level `extern_path`) | Dropped | raw `i32` | None (pbjson add-on) | Partly (`bytes`, `unsafe` string merge) |
| rust-protobuf 3 | No | `HashMap` by number | `EnumOrUnknown` | Reflection-based, no `Any` | Partly (47 `unsafe` lines) |
| google-protobuf 0.x | No | Kernel-held, no API | `i32` newtype, open/closed split | None | No (C via FFI) |
| buffa 0.9 | Proposed (#490), infallible | Ordered list, default on | `EnumValue<T>` | Conformant | Yes for default codec |
| gin-tonic 0.8 | Yes, fallible, `String` errors | Not studied | – | Not studied | Likely (0 `unsafe`) |

So **RustPB's `TypeMapper` would be new in Rust**. Mapping a message-typed field to a domain type while keeping the generated message for wire and JSON is new as well: today that needs a hand-written `Message` impl ([buffa guide](https://github.com/anthropics/buffa/blob/main/docs/guide.md)). That is RustPB's case for `Timestamp` → a time type.

The design's shape matches what working crates converged on. Decoding is fallible and surfaces as a typed decode error (buffa's `from_wire -> Result<_, DecodeError>`). The mapper is a separate type, which sidesteps the orphan rule. buffa documents the cost of skipping that: custom element types must be crate-local "because an emitted `impl ForeignTrait for ForeignType` only compiles when the element type is local". buffa then had to build a remote-derive crate to cut the "newtype tax" ([DESIGN.md](https://github.com/anthropics/buffa/blob/104716922c/DESIGN.md#L552), [buffa #212](https://github.com/anthropics/buffa/issues/212)).

The design does better than gin-tonic in one respect: gin-tonic collapses mapper failures into `ProtoError::Custom(String)`, and RustPB's `DecodeError::Map { field, source }` keeps the error's structure.

Two cautions carry over:

- **A semantic mapper can silently change bytes.** gin-tonic's `Uuid` mapper re-encodes a hyphenated UUID string as the 32-digit "simple" form ([uuid.rs](https://codeberg.org/cemoktra/gin-tonic/src/commit/e31fae4f1f63811b119c3efac805f10a85c600f5/core/src/types/uuid.rs#L21)). The re-encoded bytes differ from what came in.
- **Custom types and JSON interact by position.** buffa calls this "the most common stumbling point": a custom string in a repeated, oneof or map position needs its own `Serialize`, unlike a singular one ([custom-types README](https://github.com/anthropics/buffa/blob/104716922c/examples/custom-types/README.md)). RustPB's rule, "a mapped field prints its *base* value", avoids this only if every position goes through `to_base` and the base type's serializer. Custom types must never need serde impls of their own.

## Every advisory is a denial of service through an unbounded path

The security record is short and uniform:

| Advisory | Crate | Unbounded path | Fixed in |
|---|---|---|---|
| RUSTSEC-2020-0002 ([OSV](https://api.osv.dev/v1/vulns/RUSTSEC-2020-0002)) | prost | Unbounded recursion while decoding nested input (fixed by a general decode recursion limit). The advisory calls it potentially unsound "on architectures without stack probes" | 0.6.1 |
| RUSTSEC-2019-0003 ([OSV](https://api.osv.dev/v1/vulns/RUSTSEC-2019-0003)) | rust-protobuf | `Vec::reserve()` on a user-supplied length | 2.6.0 |
| RUSTSEC-2024-0437 / CVE-2025-53605 ([RustSec](https://rustsec.org/advisories/RUSTSEC-2024-0437.html)) | rust-protobuf | Unknown-group recursion that bypassed the 100-level limit message decoding already had | 3.7.2 |
| RUSTSEC-2021-0073 ([OSV](https://api.osv.dev/v1/vulns/RUSTSEC-2021-0073)) | prost-types | Panic converting an out-of-range `Timestamp` to `SystemTime` | `TryFrom`, 0.8.0 |

Outside RustSec the pattern repeats:

- **quick-protobuf** has an open heap out-of-bounds read: `read_len` sets `end = start + len` without clamping ([#273](https://github.com/tafia/quick-protobuf/issues/273)). Uninitialized-memory and Miri reports sit beside it ([#270](https://github.com/tafia/quick-protobuf/issues/270)–[#274](https://github.com/tafia/quick-protobuf/issues/274)).
- **micropb** 0.7.0 fixed an unbounded-recursion DoS and missing wire-type checks ([#44](https://github.com/YuhanLiin/micropb/issues/44), [#45](https://github.com/YuhanLiin/micropb/issues/45)).
- **protox** 0.10.0 fixed a stack overflow on deeply nested `.proto` *sources* ([CHANGELOG](https://github.com/andrewhickman/protox/blob/main/CHANGELOG.md)).
- **buffa** 0.9.2 was mostly hardening. One bug was an extension-merge path that "gave every wire record its own full allowance" ([CHANGELOG](https://github.com/anthropics/buffa/blob/104716922c/CHANGELOG.md#L9-L30)). Its author cautions that a green conformance run is "necessary but not sufficient", since a security review found four issues anyway ([DEV post](https://dev.to/iainmcgin/zero-copy-protobuf-and-connectrpc-for-rust-1m3e)).

The lesson for RustPB is structural. The design's §4.1 point 5 says RustPB **owns** its message merge, its map-entry decode and its builder, and borrows only prost's scalar primitives and `skip_field`. Every bound prost enforced inside its own `Message` machinery is therefore RustPB's job now:

- **Recursion.** One depth budget must thread through RustPB's nested-message decode, map-entry decode and prost's `skip_field` for unknown groups.
- **Allocation.** No `Vec::with_capacity` may come from a declared length or a packed byte count without first checking it against the bytes that remain. rust-protobuf caps any reservation at 10 MB and grows as bytes arrive ([coded_input_stream](https://github.com/stepancheg/rust-protobuf/blob/0118c79e51c8d54ac40deb8b82631ddef81fb00e/protobuf/src/coded_input_stream/mod.rs#L50-L116)).
- **Encoding.** prost has no depth limit on encode, so "it is possible to encode a message that cannot be decoded anymore" ([#736](https://github.com/tokio-rs/prost/issues/736)). The same holds for a Rust value nested deeper than the decoder's limit of 100 (C++'s default, which prost and rust-protobuf copy). RustPB should decide that case explicitly rather than inherit it.
- **The JS target.** A stack overflow there is a catchable `RangeError` rather than an abort, so a caller that catches errors can carry on with half-merged state. Depth limits matter at least as much in the browser.

The design's §6.4 fixtures cover truncation, a length past the end, overlong varints and groups. They do not yet include a **depth-bomb fixture** (nested messages, nested unknown groups, nested map values past the limit) or a **huge-length-prefix fixture**. Every advisory above would be caught by one of those two.

At this revision the design rejected groups outright (§6.4 listed "a group" as invalid → `DecodeError`). If ScalaPB's recorded result agrees, the CVE-2025-53605 class disappears, because no group recursion exists. If ScalaPB instead skips or keeps unknown groups, the skip path needs the shared budget. The fixture decides, as the design intends.

Time conversions are the second exposure. prost-types shipped a run of parser fixes in 0.13.2: date-time parsing, "'+' is not a numeric digit", long second fractions, negative fractional durations ([CHANGELOG](https://github.com/tokio-rs/prost/blob/v0.14.6/CHANGELOG.md)). It then added fuzz targets for exactly those parsers. RustPB's `Timestamp` → `Instant` mappers (open question 6) sit on the same boundary. The fallible `TypeMapper` is the right shape for them. They also deserve the same fuzzing, because an out-of-range timestamp must become a `MapError`, never a panic.

## Byte-compatibility bugs hide in defaults, wire types and size arithmetic

The byte-level bugs that lived longest were never in varint arithmetic. They were in decisions made around it.

**Packedness, the bug aimed squarely at RustPB.** A proto3 repeated scalar is packed by default. prost read `options.packed()`, which returns the descriptor default `false` once a field has any options message at all. So "a proto3 repeated packable field [with] any field option set (e.g., `[deprecated = true]` or custom extensions)" was emitted with `packed = "false"`, which "changes the wire encoding from packed to unpacked". The bug was open from January 2024 until July 2026 ([#976](https://github.com/tokio-rs/prost/issues/976), [PR #1399](https://github.com/tokio-rs/prost/pull/1399)). rust-protobuf had the same class of bug, "Default to packed for repeated primitives in proto3" ([CHANGELOG](https://github.com/stepancheg/rust-protobuf/blob/0118c79e51c8d54ac40deb8b82631ddef81fb00e/CHANGELOG.md)).

In RustPB nearly every interesting field carries `[(rustpb.field)...]` options, including the repeated mapped scalars in §4.1's table. rustpb-build must read the raw optional `packed` value and fall back to the proto3 default. Golden bytes for a repeated mapped `int64` field with options must be in milestone 1.

**Wire-type mismatches on known fields.** prost's scalar `merge` functions reject a known field number that arrives with the wrong wire type (`UnexpectedWireType`, [wire_type.rs](https://github.com/tokio-rs/prost/blob/v0.14.6/prost/src/encoding/wire_type.rs#L37-L42)). Its maps forgot the check until 0.14.6: "a map field sent with e.g. wire type `Varint` had its following bytes reinterpreted as an entry length and decoded successfully". A fuzz-corpus case had been asserting the wrong round trip ([PR #1473](https://github.com/tokio-rs/prost/pull/1473)).

This touches RustPB twice. First, RustPB owns map-entry decode (§4.1 point 5), so it must add the outer check itself. Second, reusing prost's scalar `merge` imports prost's *policy*. ScalaPB's generated parser most likely dispatches on the full tag, field number plus wire type, and sends a mismatched tag to the unknown-field branch. That would keep the field as unknown rather than fail. This is unverified here. §6.4 has no row for it, and it should get one: a known field number with each wrong wire type, packed and unpacked, recorded against ScalaPB.

**Oneof write position.** prost sorts fields by tag but writes a oneof "in the position of their lowest tag, regardless of the currently occupied variant". Its own source flags this with a TODO ([prost-derive lib.rs](https://github.com/tokio-rs/prost/blob/v0.14.6/prost-derive/src/lib.rs#L84-L101)). The design's decision 4 says RustPB writes "the same kind of code" as prost-derive in field-number order, citing `ProtobufGenerator.scala:676`. Take a oneof with members 2 and 5 around a plain field 3. When member 5 is set, prost-style emission writes 5 before 3. Strict number order writes 3 before 5. The ScalaPB generator line should be checked for oneof members specifically, and a golden case with interleaved oneof members added.

**Negative numbers and size arithmetic.** C++ writes a negative `int32` as a 10-byte sign-extended varint, confirmed by the rust-protobuf maintainer ([#758](https://github.com/stepancheg/rust-protobuf/issues/758)). rust-protobuf still has an open bug that breaks this rule in one place. A packed repeated enum holding unknown value −1 is written with a length prefix of 5 and 10 bytes of varint, so the output cannot be parsed again ([#766](https://github.com/stepancheg/rust-protobuf/issues/766)). The cause was a size function and a write function that disagreed. RustPB's `Unrecognized(i32)` can hold −1. A packed repeated enum with `Unrecognized(-1)` is a mandatory fixture. Size and write must share one owner. prost's fuzz oracle, "`encoded_len` equals bytes written, and decode∘encode∘decode is stable" ([tests/src/lib.rs](https://github.com/tokio-rs/prost/blob/v0.14.6/tests/src/lib.rs)), should be RustPB's first fuzz target.

**Negative zero.** prost's "is default?" test is `-0.0 == 0.0`, so a proto3 implicit-presence `-0.0` is dropped on encode ([#1177](https://github.com/tokio-rs/prost/issues/1177)). buffa deliberately writes it ([json_helpers.rs](https://github.com/anthropics/buffa/blob/main/buffa/src/json_helpers.rs)). The design's encoding rule says "a scalar not equal to the base default". Which equality it means decides the bytes. ScalaPB on the JVM probably compares with `!=`, which also drops `-0.0`, but this is unverified. RustPB should match ScalaPB rather than upstream C++, and pin the choice with a fixture in both binary and JSON.

**Merge versus replace.** rust-protobuf replaces a repeated singular message instead of merging it, in both plain and oneof positions ([rt/message.rs](https://github.com/stepancheg/rust-protobuf/blob/0118c79e51c8d54ac40deb8b82631ddef81fb00e/protobuf/src/rt/message.rs#L8-L19)). That breaks the wire rule that singular embedded messages "are merged" ([encoding guide](https://protobuf.dev/programming-guides/encoding/)). The design already follows this lesson in detail: §4.1 merges base values before mapping, and §6.4 has fixtures for message fields and oneof variants appearing twice.

**Unknown-field storage order.** prost's eight-year gap is the clearest argument for the design's choice to preserve unknown fields from day one. A user reported data loss in a read-modify-write database workflow, which is RustPB's exact use case ([#2](https://github.com/tokio-rs/prost/issues/2)). How to store them is a separate question:

- rust-protobuf keys a `HashMap` by field number, which loses the interleaving ([unknown.rs](https://github.com/stepancheg/rust-protobuf/blob/0118c79e51c8d54ac40deb8b82631ddef81fb00e/protobuf/src/unknown.rs#L224-L237)).
- buffa keeps an ordered `Vec<UnknownField>` ([DESIGN.md](https://github.com/anthropics/buffa/blob/104716922c/DESIGN.md#L425-L450)).
- pilota keeps raw byte chunks ([codegen](https://github.com/cloudwego/pilota/blob/8239e1e20b/pilota-build/src/codegen/pb/mod.rs#L578)).

For RustPB the target is neither "raw order" nor "canonical". It is whatever ScalaPB's own unknown-field set re-emits. §6.2 already compares unknown fields by value, which suggests ScalaPB regroups them. Settle that against ScalaPB's `UnknownFieldSet` source, then choose the storage that reproduces it.

Equality also needs a decision. Google refuses `PartialEq` because "it [is] not possible to canonicalize unknown fields" ([#23058](https://github.com/protocolbuffers/protobuf/issues/23058)). ScalaPB includes them in case-class equality. The design derives `PartialEq`, and it should say that unknown fields take part, with Google's caveat documented.

**Two more traps.** Overflow bits in a 10th varint byte are rejected by buffa but discarded by C++ and prost ([DEV post](https://dev.to/iainmcgin/zero-copy-protobuf-and-connectrpc-for-rust-1m3e)). §6.4 tests "a varint over 10 bytes" but not a valid-length varint with overflow bits, so add one. Also, prost's `unsafe` `as_mut_vec` string merge was once unsound on invalid UTF-8 ([#193](https://github.com/tokio-rs/prost/issues/193)), and RustPB reuses that string codec. This is safe natively today, but it is the code §7 expects rust-js to choke on.

## JSON breaks wherever serde's defaults leak through

Three architectures exist for proto3 JSON in Rust:

- **Generated explicit impls:** pbjson, buffa, prost-canonical-serde.
- **Reflection:** prost-reflect, protobuf-json-mapping.
- **Plain `#[derive(Serialize)]`:** prost-wkt.

The third simply does not produce ProtoJSON. prost-wkt has open issues for int64 as numbers, bytes as integer arrays, enums as `i32`, and oneofs as tagged enums ([prost-wkt issues](https://github.com/fdeantoni/prost-wkt/issues)). buffa's guide says the mapping "cannot be satisfied by plain derive alone" ([guide](https://github.com/anthropics/buffa/blob/main/docs/guide.md)). The design's choice of written-out impls (§5) is therefore correct. The subtler lesson is that even generated impls inherit serde and serde_json behaviour at the edges:

- **Floats.** pbjson passes `f64` straight to serde_json, which writes NaN and ±Infinity as `null`, an issue open since 2023 ([pbjson #106](https://github.com/influxdata/pbjson/issues/106)). serde_json 1.0.147 also switched its float formatter from ryu to zmij. A formatter swap inside a dependency bump can change digits, which is fatal for a "same JSON as the Scala printer" contract. RustPB needs its own float writer, matched digit-for-digit against scalapb-jsoniter's output and pinned by goldens.
- **Timestamps and durations.** pbjson formats `Timestamp` with chrono's `to_rfc3339()`, and its own test asserts `"…+00:00"` instead of `Z` ([timestamp.rs](https://github.com/influxdata/pbjson/blob/main/pbjson-types/src/timestamp.rs)). prost-wkt's Duration goes through `f64` and mishandles signs ([prost-wkt Duration](https://github.com/fdeantoni/prost-wkt)). The upstream conformance suite caught Protobuf-ES writing "-0.1s" as "0.1s" ([Buf blog](https://buf.build/blog/protobuf-conformance)). RustPB's time mappers serialize their *base* message, so the base `Timestamp`/`Duration` writers must be RustPB's own, never the time crate's display impl.
- **Enum aliases.** Crates that reuse a Rust enum's `FromStr` cannot parse `allow_alias` names ([pbjson #123](https://github.com/influxdata/pbjson/issues/123)). Six of prost-canonical-serde's twenty JSON conformance failures are alias cases ([failure list](https://github.com/xyzzyz/prost-canonical-serde)). Generate a name → value table holding every alias, and print the first declared name. This matters even more if open question 4 strips or re-cases Rust variant names, because JSON must keep the proto names whatever Rust calls the variants.
- **Unknown enum values.** pbjson errors on them or maps them to the default, and a commenter wrote: "It really destroys the forward-compatibility of protobufs" ([pbjson #92](https://github.com/influxdata/pbjson/issues/92)). buffa writes `Unknown(n)` as the integer. The design specifies this only for *standalone* enums. Enum *fields* holding `Unrecognized(n)` need a fixture against scalapb-jsoniter in both directions.
- **Hostile input.** buffa clamps serde size hints to 4096 against hostile deserializers. It documents that JSON parsing is not bounded by binary decode limits ([#330](https://github.com/anthropics/buffa/issues/330)), and that enabling serde_json's `arbitrary_precision` anywhere in a build breaks number parsing ([#482](https://github.com/anthropics/buffa/issues/482)). Cargo feature unification makes the last one a time bomb in a large workspace.

Three of the design's choices hold up well against this prior art.

First, **one fixed behaviour plus an explicit `to_json_including_defaults` function** is better than the alternatives. Serde's `Deserialize` takes no context, so buffa passes parse options through a thread-local under `std` and a process-global under `no_std` ([json.rs](https://github.com/anthropics/buffa/blob/main/buffa/src/json.rs)). That ambient state would need its own lowering in rust-js. RustPB has no options, so it has nothing to lower.

Second, **deferring to scalapb-jsoniter 0.1.2's leniency** is the right call for a migration, and the spec explicitly allows "ignore unknown fields". But the prior art sharpens open question 7. Every Rust JSON reader studied accepts the proto field name as well as `json_name`:

- pbjson's `visit_str` matches both ([message.rs](https://github.com/influxdata/pbjson/blob/main/pbjson-build/src/generator/message.rs));
- prost-reflect falls back to `get_field_by_name`;
- protobuf-json-mapping cites the spec in a comment;
- prost-canonical-serde injects both spellings.

The spec says parsers *must* accept both ([ProtoJSON](https://protobuf.dev/programming-guides/json/)). So 0.1.2's silent drop is a defect that the whole ecosystem avoids, not one interpretation among several. That strengthens the case for fixing it on both sides together.

Third, **mapping `Struct`/`Value` to a raw-JSON type** avoids pbjson's open bugs, where `null` decodes to `Value { kind: None }` ([#100](https://github.com/influxdata/pbjson/issues/100)) and integers over 16 digits fail ([#139](https://github.com/influxdata/pbjson/issues/139)).

The design does not mention **`google.protobuf.Any`**. If any of the 858 files uses it, JSON needs a type registry, and the options are uneven:

- prost-wkt's `typetag` + `inventory` registry relies on linker sections, which cannot exist in rust-js output.
- prost-reflect's descriptor pool ships descriptors into the bundle.
- buffa's explicit, user-installed registry filled by generated `register_types` functions works anywhere ([any_registry.rs](https://github.com/anthropics/buffa/blob/main/buffa/src/any_registry.rs)).

rust-protobuf never implemented `Any` JSON at all ([print.rs](https://github.com/stepancheg/rust-protobuf/blob/0118c79e51c8d54ac40deb8b82631ddef81fb00e/protobuf-json-mapping/src/print.rs#L42-L249)). A count of `Any` fields belongs in §2's table.

## Conformance is necessary, ScalaPB differential is sufficient, fuzzing finds the rest

The testing practices split cleanly by outcome. The projects with the fewest spec deviations run Google's conformance runner with an **exact-match failure list**, where a listed test that passes is also an error:

- prost-reflect runs binary, JSON and text with empty lists under `--enforce_recommended`.
- buffa runs empty lists across nine codec modes (std, no_std, views, reflection, table…), and every one of its nine `known_failures` lists is empty ([conformance/](https://github.com/anthropics/buffa/tree/104716922c/conformance)).

prost runs binary only. It answers every JSON request "not supported", and its two listed failures are both unknown-field round trips ([failing_tests.txt](https://github.com/tokio-rs/prost/blob/v0.14.6/conformance/failing_tests.txt)). Its byte bugs, the packed default and the map wire type, survived because conformance exercises only two test messages. The suite's reach is clearest in Buf's JavaScript survey: protobufjs passed about 31% of required tests when Buf launched its survey, while Protobuf-ES passed 100% (Buf's README now shows zero failures for both) ([Buf blog](https://buf.build/blog/protobuf-conformance)).

RustPB's §6 is strong on the part no other project has: a ScalaPB-generated golden corpus, real stored records, hand-built decoding fixtures recorded against ScalaPB, and mutations. That is the right primary oracle, because "conformance covers spec behavior, not 'match implementation X'". Three practices from the ecosystem would close its remaining gaps.

The **upstream conformance runner** is a cheap second oracle for proto3 binary. It also documents JSON deviations: RustPB's JSON failure list *is* the list of places where scalapb-jsoniter 0.1.2 departs from the spec, kept honest by the exact-match rule. Running the same testee compiled through rust-js gives the browser a third oracle, and buffa's experience says to treat it as a separate mode with its own list.

**Fuzzing** is missing from §6 entirely. prost runs libFuzzer round-trip targets on every pull request through OSS-Fuzz's CIFuzz ([cifuzz.yml](https://github.com/tokio-rs/prost/blob/v0.14.6/.github/workflows/cifuzz.yml)). It added fuzzers for its date and duration parsers after their bugs, and turned some proptests into Kani proofs, which cover only prost-types' `Timestamp` and `Duration` arithmetic, never the wire varint code ([CHANGELOG 0.13.2](https://github.com/tokio-rs/prost/blob/v0.14.6/CHANGELOG.md), [KANI.md](https://github.com/tokio-rs/prost/blob/v0.14.6/KANI.md)). RustPB's natural target goes further: decode mutated bytes in both RustPB and ScalaPB and compare the outcomes. That generalizes §6.4's hand-built fixtures, seeded with one regression input per advisory above.

**Front-end identity tests** guard the input. rust-protobuf checks that its pure-Rust parser and `protoc` produce identical codegen. protox compares its descriptors against protoc's output ([protox README](https://github.com/andrewhickman/protox/blob/main/README.md)). RustPB parses with protox while ScalaPB uses protoc. Any difference in computed `json_name`, packedness or option values across the 858 files would silently fork the JSON or the bytes. One test that compares the two descriptor sets for every production file removes that risk.

Custom options need the same care. prost-types' `FieldOptions` cannot hold extension values, because prost drops unknown fields. pilota-build likewise "discarded the option value" of custom options ([pilota #372](https://github.com/cloudwego/pilota/issues/372)). gin-tonic reads its option through a descriptor pool. rustpb-build must read `(rustpb.*)` options through a representation that keeps extensions, such as prost-reflect's pool, which protox already builds on, or it will see no mappings at all.

## Conclusion

The ecosystem's history reframes what "proven" means for RustPB. prost's varint arithmetic is well tested: fuzzed on every pull request and stable for years, though not Kani-proved (its proofs cover only prost-types' `Timestamp` and `Duration`). prost's *decisions* are not: packedness, wire-type policy, oneof placement, map checks and unknown fields. The design borrows the first and, through "the same kind of code", risks inheriting the second. The two most dangerous divergences from ScalaPB would not come from RustPB's novel features, which the design treats with unusual rigor. They would come from small policies copied from prost by default: the packed-with-options bug and the wrong-wire-type rule. Both are cheap to pin with a fixture today and expensive to find in a topic shared with Scala services later.

The second shift concerns where RustPB's real oracle lives. Every mature project leans on Google's conformance runner. RustPB's contract is "equal to one ScalaPB deployment", so conformance becomes a secondary oracle, valuable mostly as a *failure list that documents* each deliberate deviation. ScalaPB differential fuzzing, which no Rust project has needed before, becomes the primary one. RustPB will also be the only pure-Rust protobuf runtime that must lower cleanly to JavaScript. That pushes it toward femtopb's zero-`unsafe`, plain-data style, and puts its JS build into the conformance and fuzz loop as a first-class target, not an afterthought.
